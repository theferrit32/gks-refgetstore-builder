# Add superseded and retired RefSeqGene versions

The store gained every earlier version of each current RefSeqGene (`NG_`)
accession, and every version of `NG_` accessions since retired from
`gene_RefSeqGene`: 2,501 sequences fetched one accession at a time from NCBI
E-utilities `efetch`. NCBI's RefSeqGene FTP publishes only current versions.

The accession list is `accession_lists/refseqgene_superseded.txt`, generated by
`gks-refgetstore refseqgene-history --seqrepo-aliases <seqrepo 2024-12-20>/aliases.sqlite3`
from `gene_RefSeqGene` (6,837 current versions) and seqrepo's `NCBI` `NG_`
aliases. It is the `refseq_human_refseqgene_superseded` seqset in
`sources.toml`.

## Result

| | before | after |
| --- | ---: | ---: |
| sequences | 1,779,052 | 1,781,533 |
| collections | 235 | 236 |

- `fetch`: all 2,501 accessions retrieved in 13 batches, no rate-limit
  responses; 101,197,269 bytes, SHA-256 `7756a0cf…5b8b64`.
- Selective `build --seqset refseq_human_refseqgene_superseded --force-lock`:
  one collection, `MD6Ozcf38_BHxS91ZZPRPDImssycpDC8`. 2,481 of its sequences
  are new; 20 were already in the store from other sources. 2,494 `refseq`
  aliases were added; 7 were already present with the same digest.
  `--force-lock` was required only because the new file had no lock baseline.
- `verify`: pass. `verify-corpus` ([`artifacts/verify_corpus.py`](artifacts/verify_corpus.py)):
  every record round-trips through gtars, including those with `K R S Y`
  ambiguity codes; the 2,146 records seqrepo also has match its digests
  exactly; the other 355 are versions seqrepo never captured; every accession
  resolves in the store.

The store was built from the code in commit `78c8ef3`, then uncommitted, so the
lock records `e72669d-dirty`.

## Current RefSeq feeds had been repacked

`sync` was not used. Its dry run ([`artifacts/feed-comparison.txt`](artifacts/feed-comparison.txt),
which also holds the comparison below) reported, besides the new source, a ninth RefSeqGene shard missing from the
cache and the `mRNA_Prot` `human.16` shards gone upstream, which would have
removed two collections. A record-level comparison of the cached feeds with the
then-current upstream files found that both feeds had been re-exported:

| | RefSeqGene | mRNA_Prot |
| --- | ---: | ---: |
| shard MD5s changed | 8 of 8, plus new shard 9 | 30 of 30; shard 16 dropped |
| records cached → upstream | 6,844 → 6,844 | 471,504 → 471,431 |
| accession.versions added / removed | 0 / 0 | 78 / 151 |
| same accession.version, different bytes | 0 | 0 |
| records in a different shard | 4,089 | 213,405 |

None of shard 16's 1,495 records were removed upstream; they moved to other
shards. Shards of these feeds are packaging, not units of content, so ingesting
each as its own collection turns a repack into wholesale removal and
re-ingest. The store keeps the 2026-10-07 snapshot of both feeds.
